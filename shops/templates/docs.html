How paying works

{{ brand }} uses x402: the old, never-used HTTP status 402 Payment Required, finally put to work. Payment details travel in three HTTP headers. Each one is JSON, base64-encoded.

agent →
GET /api/price?symbol=ETH (no payment yet)
← shop
402 + {{ h_required }}: the bill
agent →
same request + {{ h_signature }}: signed USDC authorization
← shop
200 + data + {{ h_response }}: the receipt

The shop never holds a key for the buyer. The buyer signs an EIP-3009 transferWithAuthorization message; a facilitator checks the signature and submits it on-chain.

1 · The bill: {{ h_required }}

Call any paid endpoint without paying and you get 402. The bill is in the header (base64) and, for convenience, also in the body. accepts lists the payment options; we offer one.

Below: a bill built by the same code the paywall uses. Click to get one over HTTP.

2 · The payment: {{ h_signature }}

The agent copies the option it accepts into accepted, signs an authorization moving exactly amount to payTo, base64-encodes this JSON and retries the same URL with it as the {{ h_signature }} header.

expected shape → PaymentPayload (before base64)placeholder signature
{{ payment_json }}

We reject the payment (402 again, with a reason in error) if the amount, receiver, token, network or signed authorization don't match the bill exactly.

3 · The receipt: {{ h_response }}

Once the payment settles, the response is 200 with the data, plus a receipt naming the transaction and the payer.

Atomic units

      
USDC has {{ decimals }} decimals, so amounts are whole numbers of its smallest unit: 1 USDC = 1,000,000 atomic units. Whole numbers avoid rounding errors with money.

      
10000 atomic units = 10000 ÷ 1,000,000 = $0.01
